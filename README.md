# bus-seat-prediction

**결론: 광역버스 M6117의 홍대 도착 좌석 수를 맞히는 점 예측은 구조적 한계가 있어서, 문제를 "홍대에서 15석 이하(빠듯함)일 확률"로 다시 정의했다.** 데이터를 281트립에서 1,977트립으로 7배 늘려도 15석 이하 구간의 MAE는 11.3에서 11.8로 그대로였다. 확률로 바꾸면 AUC 0.92~0.96을 얻는다(시간순 분할 포함). 단, 15석 이하는 만차가 아니라 "빠듯함"의 대리 지표이고, 실제 탑승 불가(0석) 확률은 표본이 부족해 추정하지 못했다.

## 1. 문제

**출발점**은 통근하면서 느낀 "배차 대기와 만차가 지도 앱의 소요시간에 반영되지 않는 느낌"이다. 지도 앱의 정확도는 이 프로젝트에서 직접 측정하지 않았다. M6117은 시간표가 매일 바뀌어 정적 시간표로 예측하기 어렵다고 보고, 실시간 도착·좌석 데이터를 장기간 쌓기로 했다.

**이 프로젝트가 실제로 한 일**은 광역버스 좌석 소진 패턴의 정량화와, 홍대 도착 시 좌석이 빠듯할 확률의 예측이다.

**데이터가 보여준 것**
- M6117의 홍대 정류소에서 만차(0석)는 드물었다(표본 5건 미만).
- G6000은 관측 초기(8월 분석 기준)에 거의 항상 여유가 있었다(5석 이하 0건).
- "홍대에서 못 탄다"는 체감은 데이터로 강하게 확인되지 않았다.
- 확인된 것은 17-18시에 "좌석이 빠듯한" 경우(홍대 15석 이하)가 집중된다는 점뿐이다.
## 2. 데이터와 파이프라인

경기버스정보(GBIS) Open API의 도착정보 조회를 정류소별로 호출해 전 노선을 저장한다. 노선 필터링은 분석 시점에 한다.

```
GBIS API ──(2분 간격, 16:00~22:58, cron)──> collect.py ──> SQLite(arrivals, raw JSON 보존)
                                                               │
                                       analysis/*.py (읽기 전용으로 DB를 연다)
```

- 대상: M6117 구래/김포 방면 4개 정류소(공덕역, 신촌, 홍대입구, 합정). 상류 정류소를 함께 찍어야 좌석이 줄어드는 궤적이 보인다.
- 실행: GCP VM(Always Free 사양)에서 cron으로 운영. 초기에는 Windows 작업 스케줄러(`scripts/`)로 돌렸다.
- API 일일 한도(개발계정 1,000건) 안에서 하루 약 840회 호출.
- 수집 시작 2026-07-22. **2026-11-05 16:10 ~ 11-15 사이 약 10일은 수집이 중단되었다**(VM 무료체험 종료). 복구할 수 없고, 분석은 11-01까지 데이터로 했다.

## 3. 데이터 함정

| 함정 | 처리 |
|---|---|
| `remainSeatCnt`가 세 가지 상태: `""` = 버스 없음, `-1` = 버스는 오지만 좌석정보 미제공, 그 외 정수(0 포함) = 실제 좌석 수 | `-1`을 만석으로 읽으면 만차 빈도가 부풀려진다. `seat_info_available` 컬럼으로 구분하고 `-1`은 NULL로 저장 |
| 두 번째 버스가 없으면(`predictTime2` 공백) `remainSeatCnt2`가 `"0"`으로 옴 | predictTime이 비면 좌석은 NULL로 저장. 원본 문자열은 `raw`에 그대로 보존 |
| 같은 차량이 여러 정류소에 동시에 예측으로 잡힘 | 차량번호(plateNo)로 궤적 추적. **같은 차량이라도 30분 이상 공백이면 별도 트립으로 분리** (하루에 왕복을 여러 번 돎) |
| 정류소 통과 순서를 첫 관측 시각으로 정렬하면 API 호출 순서가 그대로 반영됨 | **last-seen(마지막 관측 시각) 기준으로 정렬** |
| SQLite `strftime`이 KST 문자열을 UTC로 변환해 9시간 밀림 | 문자열 슬라이싱 또는 `datetime.fromisoformat`으로 파싱 |

## 4. 분석 흐름

1. **선형 회귀 (8월, 281트립)**: 공덕 좌석 → 홍대 좌석, 전체 MAE 4.0. 그러나 홍대 15석 이하에서는 MAE 11.3으로 무너짐. 당시에는 "표본 부족"이 원인이라고 진단했다.
2. **재분석 (11월, 1,977트립)**: 전체 MAE 4.17, 15석 이하 MAE 11.78. 데이터가 7배가 되어도 개선되지 않아 **8월의 "표본 부족" 진단은 틀렸다**. 20개 시드 반복에서도 같았다.
3. **17-18시 특화 모델**: 피크 시간대 전용 모델은 홍대 실제값 조건부로 보면 개선(+3.0석)처럼 보이지만, 운영 가능한 정의(공덕 좌석 30석 이하)로 보면 +0.52석(95% CI -0.52~+1.59)로 유의하지 않다. 개선의 실체는 회귀식 절편 이동이다.
4. **확률 예측으로 전환**: "홍대 15석 이하일 확률"을 로지스틱 회귀로 예측. 피처는 공덕 좌석, 17-18시 여부(공덕 통과 시각 기준), 요일.

> 8월 수치(MAE 4.0, 11.3)는 당시 분석 보고 기준이며, 11월 재분석에서 재현한 것은 281트립 수까지다.

### 스크립트 ↔ 분석 단계

| 단계 | 스크립트 |
|---|---|

| 1차 분석: 모델1 오차 분해(좌석 구간별·시간대별 MAE) | `analysis/aug2026/error_breakdown.py` |
| 1차 분석: "빡빡한 상황"(공덕 30석 이하 등) 특화 모델 실험 | `analysis/aug2026/specialized_model.py` |
| 1차 분석: 수요일 완전 궤적 저조의 원인 진단(수집 누락인지 데이터 결측인지) | `analysis/aug2026/wed_investigate.py` |

## 5. 결과

상세 표는 [docs/results_2026-11-02.md](docs/results_2026-11-02.md). 타깃은 **홍대 좌석 15석 이하**(전체 트립 1,977건 중 112건, 5.7%).

| 모델 | 검증 | AUC | Brier | ECE |
|---|---|---|---|---|
| F2: 공덕 + 17-18시 | 랜덤 5-fold | 0.924 | 0.0375 | 0.76%p |
| F2: 공덕 + 17-18시 | 시간순 80/20 | 0.950 | 0.0509 | 4.18%p |
| F3: 공덕 + 17-18시 + 요일 | 랜덤 5-fold | **0.939** | 0.0344 | 1.30%p |
| F3: 공덕 + 17-18시 + 요일 | 시간순 80/20 | **0.962** | 0.0436 | 3.36%p |

- 시간순 분할은 앞 80%(~2026-10-12, 양성률 4.9%)로 학습해 뒤 20%(양성률 8.8%)를 예측한 것이다.
- ⚠️ 시간순 ECE는 테스트 396건·양성 35건 기준이고, 시간순 보정표의 구간별 n이 1~13건(F3는 최대 17건)이라 **Spearman 등 순위 지표는 근거가 약하다.**
- 룩업 예시: 17-18시 + 공덕 31~35석이면 홍대 15석 이하 비율이 27.1%(36/133), 같은 좌석수의 다른 시간대는 4.7%(10/211).
- 홍대 10석 이하를 타깃으로 한 결과는 docs에 있다(양성 45건).

> 트립 수 정의: 17-18시 트립은 공덕 통과 시각 기준 546건(예측 시점에 알 수 있는 값)이고, 홍대 도착 시각 기준으로 세면 536건이다.

### 재현 확인

재작성한 코드로 백업 DB(1,023,175행, `--until 2026-11-02`)를 재실행한 값이 원본 실행 시 보고값과 일치했다(완전 궤적 1,977, 15석 이하 112, 17-18시 546, MAE 4.17/11.78, AUC 0.939/0.962, ECE 0.76/4.18%p). **다만 원본 실행 코드가 유실되어 원본 코드와의 직접 비교는 아니다.** 일치표는 docs에 있다.

## 6. 한계

- **홍대 0석(탑승 불가) 표본이 5건 미만**이라 "탑승 불가 확률"은 추정하지 못했다. 만차는 주로 합정에서 발생한다.
- **15석 이하는 만차가 아니다.** "빠듯함"의 대리 지표일 뿐이다.
- 최근 약 3주(시간순 테스트 구간)는 15석 이하 비율이 4.9%에서 8.8%로 올랐고 확률이 과소추정된다. 원인은 확인하지 못했다.
- 같은 날 트립은 독립이 아니어서 랜덤 CV는 다소 낙관적이다. 시간순 분할이 더 엄격한 기준이다.
- 2026-11-05~11-14 약 10일 수집이 중단되었다(VM 무료체험 종료). 이 구간은 복구하지 못했다.
- 대기시간·배차간격 분석, G6000과의 대체 관계 분석은 이 저장소에서 다루지 않았다.

## 7. 재현 방법

수집한 데이터는 비공개이고, API 이용약관상 원본 데이터를 재배포하지 않는다. 따라서 수집기부터 직접 돌려야 한다.

1. 공공데이터포털에서 경기버스정보 API 활용신청 후 키 발급.
2. 환경 준비
   ```
   pip install -r requirements.txt
   cp .env.example .env      # GBIS_API_KEY= 에 키 입력
   ```
3. 수집 (2분 간격, 하루 16~23시). Linux cron 예:
   ```
   */2 16-22 * * * cd /path/to/repo && python collect.py >> logs/collect.log 2>&1
   ```
   Windows에서는 `scripts/register_task.ps1`(`-PythonW`로 경로 지정 가능).
4. 분석 (DB는 읽기 전용으로 연다)
   ```
   export BUS_DB_PATH=data/bus.db
   python analysis/reanalysis.py --until 2026-11-02
   python analysis/prob.py       --until 2026-11-02
   ```
   `--until`은 필수이며 기본값이 없다(해당 날짜 미만의 `collected_at`만 사용). DB 경로는 `--db` 인자로도 줄 수 있다.

두 스크립트는 scratchpad 유실로 보고 기준 코드를 재작성한 버전이다. 새로 모은 데이터로 돌리면 이 문서의 수치와 다른 값이 나온다.
